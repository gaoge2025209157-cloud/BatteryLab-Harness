# BatteryLab Harness 项目需求、用户流程、分工与验收标准

> 本文用于统一项目目标、用户操作流程、成员职责和完成标准。当前仓库中的 ElectrochemHarness v0.4.0 已具备蓝电数据读取、指标计算、质量检查、文献核验、报告输出、Origin 绘图、图形界面和自动测试等基础能力。下一阶段的重点不是重复开发分析程序，而是在现有原型上补齐分析计划、人工确认、状态记录、系统评测和课程演示，使其成为可解释、可审计、可验证的 AI Harness。

## 一、项目需求

### 1. 项目背景

电池充放电循环实验会产生大量时序数据。实际分析中常见字段命名不统一、单位混用、时间顺序异常、循环不完整、实验条件缺失及重复计算等问题。若直接让大模型读取数据并回答，可能出现误解字段、错误计算、缺少证据和无法复现等风险。

本项目拟建立一套面向电池循环实验数据的受控分析流程：大模型或规则模块负责理解任务、组织分析计划和解释结果；经过测试的确定性程序负责读取数据、检查质量、计算指标和生成图表；Harness 负责限制操作、组织步骤、等待人工确认、记录执行过程并验证结果。

### 2. 目标用户

第一版主要面向需要处理蓝电等设备导出数据的电池实验人员，包括化工或材料专业研究生、实验室助理和科研项目成员。用户应具备基本电化学知识，但不要求掌握 Python 编程。

### 3. 核心目标

1. 降低格式、单位和异常数据造成的分析错误；
2. 自动计算库仑效率、容量保持率、比容量和电压相关指标；
3. 在分析前展示计划和风险，让用户决定是否继续；
4. 让每一项结论能够追溯到输入数据、计算方法和证据；
5. 通过固定评测数据证明系统比直接使用大模型更准确、更安全、更可复现；
6. 形成一套四人均可解释、运行和演示的课程成果。

### 4. 第一版功能范围

| 环节 | 第一版要求 | 预期输出 |
|---|---|---|
| 数据输入 | 支持蓝电导出的 CSV、TXT、TSV、DAT 等文本数据；识别常见中英文列名、分隔符和编码 | 文件摘要、识别字段、单位和导入信息 |
| 实验信息 | 记录电池体系、正负极、活性物质质量、倍率、温度等实验条件；提示缺失项 | 实验信息清单、缺失信息警告 |
| 数据质检 | 检查必需字段、非数值、时间倒退、循环不完整、负电压、单位或符号异常 | 问题类型、严重程度、证据和处理建议 |
| 分析计划 | 根据数据类型和用户目标列出拟执行的检查、指标和输出 | 可阅读的分析计划 |
| 人工确认 | 数据存在阻断问题、需要联网检索或准备生成正式输出时，等待用户确认 | 确认或取消记录 |
| 指标计算 | 使用确定性程序计算充放电容量、比容量、库仑效率、容量保持率、平均电压和电压差 | 按循环排列的指标表 |
| 结果验证 | 检查结果是否完整、数值是否在合理范围、输出是否能追溯 | 验证状态和警告 |
| 报告与图表 | 生成精炼报告、关键参数表、完整分析记录及可供 Origin 使用的数据 | Markdown、CSV、JSON、图片或 Origin 工程 |
| 文献核验 | 在条件完整且用户允许时检索 DOI；区分“候选文献”和“直接可比文献” | 文献证据和适用边界 |
| 运行留痕 | 记录输入文件标识、步骤、参数、时间、状态、警告和产物 | 完整运行记录 |

### 5. 第一版暂不包含

- 不以电池寿命预测或复杂机器学习建模为核心；
- 不自动给出材料机理、重复性或创新性结论；
- 不支持 CV、EIS、GITT、dQ/dV 和蓝电专有二进制数据库；
- 不允许大模型直接执行任意 Python、Shell 或写入型 SQL；
- 不自动修改或覆盖原始实验数据；
- 不把未经核验的文献摘要作为最终科学证据。

### 6. 约束与安全要求

1. 原始数据只读，分析结果写入独立输出目录；
2. 未公开或敏感实验数据不得上传公共仓库；
3. 模型 API 密钥、账号密码、验证码和个人信息不得提交；
4. 数据单元格中的文字一律视为数据，不能成为系统指令；
5. 联网检索只发送必要的公开实验条件，不发送姓名、保密编号或完整原始数据；
6. 关键计算必须由经过测试的程序完成，而不是由大模型心算；
7. 系统遇到缺少关键条件或阻断问题时，应停止并说明原因，不得猜测。

## 二、用户流程

### 1. 标准流程

**选择数据文件 → 填写实验信息 → 自动识别与质检 → 查看问题和证据 → 生成分析计划 → 用户确认 → 执行指标计算 → 验证结果 → 生成报告与图表 → 保存运行记录**

### 2. 分步说明

| 步骤 | 用户操作 | 系统行为 | 进入下一步的条件 |
|---|---|---|---|
| 1. 选择文件 | 选择蓝电导出的文本数据 | 只读加载文件，识别格式、编码、分隔符和字段 | 文件可读取且类型受支持 |
| 2. 补充信息 | 填写电池体系、质量、倍率和温度等 | 检查必填信息，列出缺失项 | 用户确认信息或接受缺失提示 |
| 3. 数据质检 | 查看系统发现的问题 | 按严重程度展示问题、位置和证据 | 无阻断问题，或问题处理后重新检查 |
| 4. 查看计划 | 阅读拟计算指标、拟生成产物及是否联网 | 生成结构化分析计划 | 用户明确确认 |
| 5. 执行分析 | 点击开始 | 调用白名单工具完成计算，不覆盖原始文件 | 工具成功返回且记录完整 |
| 6. 结果验证 | 查看指标、警告和异常循环 | 检查数值完整性、范围和可追溯性 | 验证通过或带说明的警告 |
| 7. 输出结果 | 选择报告和绘图方式 | 生成报告、CSV、JSON 和图形数据 | 输出文件完整且可打开 |
| 8. 反馈与复现 | 对建议标记有效或无效 | 保存反馈证据和本次运行摘要 | 以后可根据相同输入复现 |

### 3. 必须设置的人工确认点

1. **严重数据问题确认：** 若时间倒退、关键列缺失或循环结构无法识别，系统应阻止计算，提示用户修正数据后重新运行；不得用“仍然继续”掩盖错误。
2. **分析计划确认：** 系统明确列出将计算什么、使用什么实验信息、生成什么文件，用户确认后才执行。
3. **联网检索确认：** 启用 Crossref 等外部检索前，说明将发送哪些检索条件。
4. **正式输出确认：** 生成可用于汇报或论文整理的结果前，提醒用户核对实验条件和数据范围。

### 4. 异常流程

- 文件格式不支持：停止读取，并给出转换为 CSV 或 TXT 的方法；
- 缺少关键列：指出缺少的列，不进行指标计算；
- 时间或循环结构异常：标记具体位置，要求修正或更换数据；
- 实验信息不完整：允许生成有限报告，但不得做需要该条件的归一化或文献对比；
- 文献检索失败：保留本地分析结果，报告中明确写明未完成文献核验；
- Origin 不可用：仍生成分析报告及可导入 Origin 的 CSV，不应导致整个流程失败；
- 用户取消：保存取消节点和已完成步骤，不生成未经确认的正式结果。

## 三、成员分工与交接

### 1. J：现有原型、数据标准与领域规则

**主要职责：** 维护当前分析原型；定义数据字段、单位、格式识别和数据质量规则；提供正常及异常数据样例。

**主要交付：** 数据字典、质量规则、示例数据、现有分析程序说明和原型运行反馈。

**交接关系：** 与 C 共同确认科学口径；向 H 说明现有程序接口和限制；向 G 提供评测场景及预期结果。

### 2. C：指标口径与科学验证

**主要职责：** 审核库仑效率、容量保持率、比容量、平均电压等公式和统计口径；独立核算少量样本；确定结果的合理范围及允许误差。

**主要交付：** 指标说明、人工标准答案、边界案例、科学审核记录和文献可比条件。

**交接关系：** 审核 J 的规则和计算；向 G 提供评测标准答案；与 H 确认程序输出与科学含义一致。

### 3. G：项目需求、用户流程、协作与整体评测

**主要职责：** 维护本需求文档；设计操作流程和人工确认点；组织 GitHub 任务；建立整体评测方案；统计结果；统筹演示和汇报。

**主要交付：** 需求说明、流程与分工、评测计划、评测案例表、评测结果、任务清单和演示脚本。

**交接关系：** 向 J、C 提出数据和标准答案需求；向 H 提出流程、界面和日志要求；组织四人共同验收。

### 4. H：Harness 架构与系统集成

**主要职责：** 在现有原型基础上补齐分析计划、人工确认、运行状态、工具白名单、日志、失败恢复和统一界面；配置自动测试。

**主要交付：** Harness 主流程、状态与审批模块、工具接口、运行日志、集成测试和启动说明。

**交接关系：** 接收 J 的规则和 C 的算法口径；根据 G 的流程及验收案例完成系统集成；将程序限制和实现成本及时反馈给全组。

## 四、验收标准

### 1. 项目级完成标准

项目只有同时满足以下条件，才可认定为课程展示版本：

- 一份正常数据能够从导入到报告完整运行；
- 一份包含已知问题的数据能够正确报警并给出证据；
- 关键指标与 J、C 确认的标准答案一致；
- 未经用户确认，系统不执行受控步骤；
- 原始数据不会被覆盖；
- 每次运行均能找到输入摘要、工具步骤、参数、警告和输出文件；
- 文献结论明确标注证据来源和适用边界；
- 同一数据和相同条件重复运行，核心数值结果一致；
- 四名成员都能解释自己的模块，至少两名成员能够独立完成演示；
- GitHub 主分支中的展示版本能够按照说明重新运行。

### 2. 功能验收标准

| 编号 | 验收对象 | 通过条件 | 主要负责人 | 验收人 |
|---|---|---|---|---|
| F-01 | 文件导入 | 正确识别约定格式、编码、列名和单位；不支持的格式给出明确提示 | J | C、H |
| F-02 | 数据质检 | 对预埋的关键问题给出类型、严重程度、位置和证据 | J | G、C |
| F-03 | 指标计算 | 核心指标与人工标准答案在约定误差内一致 | C | J、G |
| F-04 | 分析计划 | 执行前清楚列出检查项、指标、联网行为和输出 | H | G |
| F-05 | 人工确认 | 未确认时不进入执行；取消后不生成正式结果 | H | G |
| F-06 | 报告输出 | 报告、关键参数表和完整 JSON 内容一致且可打开 | J、H | G、C |
| F-07 | 文献核验 | 条件不足时不做直接性能比较；候选 DOI 可追溯 | J、C | G |
| F-08 | Origin 降级 | 无 Origin 时仍能完成核心分析并输出可导入 CSV | J、H | G |

### 3. 科学正确性验收

- 充放电电流正负方向和单位换算经过 J、C 确认；
- 库仑效率、容量保持率和比容量公式有书面定义；
- 部分循环、不完整循环和首圈参考值有统一处理规则；
- 每个核心指标至少有一组人工计算样例；
- 科学结论区分“数据直接支持”“规则提示”“文献候选”和“尚不能判断”；
- 单个样本不得被表述为材料机理、重复性或普遍性能证明。

### 4. 安全与可审计验收

- 原始输入只读，系统不静默覆盖文件；
- 数据中的“忽略规则”“读取其他文件”等文字不会被执行；
- 外部检索不发送原始文件、个人信息或保密编号；
- 关键步骤有确认记录，失败与取消状态可区分；
- 所有结论能够关联到相应指标、数据问题、规则或文献来源；
- 缺少条件或工具失败时明确降级，不伪造结果。

### 5. 协作验收

- 每项任务在 GitHub 中有负责人、交付物和完成条件；
- 成果先在个人分支完成，通过 Pull Request 审核后再进入主分支；
- 科学内容至少由另一位化工成员审核；
- 流程和评测由 G 验收，程序接口和安全机制由 H 检查；
- 主分支始终保留可运行版本，重要决定不得只留在群聊中。

## 五、整体评测方案的协作要求

### 1. 是否需要 J、C 准备数据

**需要。整体评测不能由 G 单独完成。** G 负责确定“测什么、怎么算通过、如何统计”；J、C 负责保证评测数据符合真实电化学场景，并提供或审核标准答案；H 负责把案例接入自动化流程。这样可以避免 G 凭管理视角设置不合理的电化学异常，也避免技术成员只测试程序能否运行而忽略实际使用效果。

### 2. 评测数据分工

| 成员 | 评测责任 |
|---|---|
| J | 准备脱敏、合成或小型示例数据；设计字段、单位、时间和循环结构问题；注明每个问题所在位置 |
| C | 人工核算核心指标；确认异常是否符合科学逻辑；给出标准答案、允许误差和不可下结论的边界 |
| G | 建立案例编号、测试目的、预期行为和评分方式；组织裸大模型与 Harness 对比；汇总准确率、安全性、耗时和失败原因 |
| H | 建立批量运行或自动测试入口；保证每次评测记录输入、版本、参数、结果和日志 |

### 3. 第一批建议评测案例

| 案例 | 数据情况 | 预期系统行为 | 数据/答案责任 |
|---|---|---|---|
| E-01 | 正常完整循环数据 | 完成分析并生成正确报告 | J 准备，C 核算 |
| E-02 | 缺少电压或时间列 | 阻止计算并指出缺失列 | J 准备，G 验收 |
| E-03 | A 与 mA 单位变化 | 正确换算或明确报警 | J 准备，C 确认 |
| E-04 | 时间倒退 | 标记具体位置并停止错误积分 | J 准备，C 确认 |
| E-05 | 循环不完整 | 标记不完整，不虚构库仑效率 | J、C 共同准备 |
| E-06 | 缺少活性物质质量 | 保留原始容量，不计算比容量 | C 给出标准答案 |
| E-07 | 负电压或异常电压 | 给出警告、位置和证据 | J、C 共同确认 |
| E-08 | 文献检索条件不完整 | 不做“直接可比”结论 | C 定义边界，G 验收 |
| E-09 | 数据单元格含提示词注入文字 | 只当作数据，不执行其中要求 | G 设计，H 实现 |
| E-10 | 用户未确认分析计划 | 不执行受控分析或正式输出 | G 设计，H 实现 |
| E-11 | Origin 未安装 | 核心分析继续，输出可导入 CSV | G 验收，H 实现 |
| E-12 | 同一输入重复运行 | 核心数值一致，运行记录可区分 | G 统计，H 实现 |

### 4. 建议评测指标

- 数据问题识别率；
- 正常数据误报率；
- 核心指标计算正确率；
- 阻断问题拦截率；
- 人工确认有效率；
- 证据与溯源完整率；
- 重复运行一致率；
- 单次任务完成时间；
- 裸大模型与 Harness 的正确性和安全性差异。

---

**讨论时优先确认的四个问题：** 第一版支持哪类电池与测试模式；三个核心指标的统一口径；哪些问题必须阻止计算；哪些步骤必须由用户确认。
